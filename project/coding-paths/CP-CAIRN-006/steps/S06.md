# CP-CAIRN-006 S06

### S06 — one commit for one path — **COMPLETE**

#### Plan

ADR-008 decisions 2 and 4, one subject: what the integrating commit may
be, and what it must carry.

**Decision 2, the integrating unit is one commit for one path.** It is
one commit from a clean trunk checkout, carrying `done`, the resolution,
the live view and the journal entry — never a merge object that brings
the branch in and edits the record in the same object, and never two
paths in one change. Both shapes happened on the adopter, and nothing
read either. `acceptance` reads the commit in which a record reached
`done` and refuses a merge object; it counts the records arriving at
`done` in one change and refuses the second.

**Decision 4, one key for the journal's path.** The rule reads the
entry's `cairn.path`, and its refusal says *declaring `path: <id>`*,
which reads as a top-level key — every one of the fifteen adopter
entries carries both, copied forward from the first. The message names
the key the checker actually reads.

Definition-of-done item advanced: the seventh.

**The planned S06 carried decision 6 as well.** It does not: decision 6
is a sweep over every blocking message in the file, with the fixture
suite asserting on the remedy, and the stale citations under `tools/`
belong with it — one reader's question, *what does this refusal tell
me*, against this unit's, *what may the integrating commit be*. They
could not be explained in three lines together.
[`plan.md`](../plan.md) is amended, the later steps shift by one, and the
definition of done is untouched: item 7 is advanced by both units.

Type `implementation`: behaviour changes, so the failing tests come
first.

Deliberately not in this unit: decision 6's remedy sweep and the
citations (S07); the `cairn-close` skill's sentence, which ADR-008
decision 2 also names — `skills/**` is row 1's surface and item 10 of
the definition of done requires it unchanged here.

- **`integrationState(file, ref)` reads what the range says about an
  integration**: the commit in which the record reached `done`, whether that
  commit is a merge object, and whether the `ready` the branch declared sits
  behind it. `statusCommit` is ADR-004 decision 1's reader, generalised from
  `activationCommit` by the status it looks for — the registration asked it of
  `running`, the integration asks it of `done`, and the walk is the same one.
- **`acceptance` refuses the two shapes decision 2 names**: an arrival carried
  by a merge object rather than by a commit of its own, and a change that takes
  more than one path to `done`. The count is asked of the change, so it holds
  in the working tree as well as in the integrating request's own run; the
  merge object is only visible where the commit exists, and the rule says so.
- **`transition` learned what its own record says.** Writing the honest
  fixture — the administrative commit, the `--no-ff` merge, then `done` in a
  commit of its own — turned it red: the range holds the merge, so the
  endpoints read `running` at the base and `done` at the head while the `ready`
  the branch declared is a commit inside it. ADR-001 decision 7 refuses the
  arrival *with no ready commit behind it*, which is a question about the
  history; the rule asked the endpoints, and would have refused every honest
  integration read from a request.
- **`journal-entry` names the key it reads** — `cairn.path`, not a top-level
  `path:` — which is how fifteen adopter entries came to carry both.
- **Four fixtures**: the honest integration, green, as the baseline the other
  two mean nothing without; the merge object carrying the edit; one commit
  taking two paths to `done`, with a second closed path on the trunk to take;
  and the entry's key, asserted on the message.

#### Review

First read, a fresh context given this unit's diff and the two criteria, and
nothing else. Ten findings; each with its disposition:

- `correctness:` the merge rule was blind to the shape it names. `git log
  <range> -- <file>` lists a merge only when it is TREESAME to no parent, so a
  branch that had already declared `done` made its own merge invisible: the
  reader followed the branch side, returned a commit that is not on the trunk
  at all, and reported no merge. The reader built the repository and showed the
  gate green on it — **fixed**: the walk is `--first-parent`, which is what the
  trunk said over time, with the fixture that evades the old reading.
- `correctness:` two arrivals were counted per COMPARISON, not per commit, so a
  request spanning two honest integrations was refused with a remedy telling
  the author to do what they had done — **fixed**, the count is per commit, and
  a fixture requires the two-integration range to be green.
- `correctness:` `readyBehind` was "some `ready` ancestor in the range", which
  an abandoned earlier `ready` satisfies, reopening the edge ADR-001 decision 7
  closes — **fixed**: it is what the record said in the commit before the
  arrival, on the trunk's own line.
- `correctness:` the reader followed one record shape and no renames, where its
  sibling deliberately walks both because a record's history is not erased by
  moving the file that carries it — **fixed** by the shared reader below.
- `correctness:` `--reverse` orders by commit date, which a rebase or a skewed
  clock can invert, while every question here is about ancestry — **fixed**,
  `--topo-order`.
- `shrink:` the `commits`/`statusAt`/`statusCommit` triple was about to exist
  twice — **fixed**: `recordHistory(range, id)` is both, and the two callers
  differ by the one flag that separates their questions, with the reason on
  each.
- `shrink:` the second path's record re-implemented the record template and the
  write-digest-rewrite dance beside it — **fixed**, the template takes the
  record it is written as, and the second path is that template.
- `correctness:` a unit test whose regex was half dead — the message contains
  no "two paths", so the alternation reduced to "some acceptance message
  mentions this id" — **fixed**, it asserts the sentence and the commit.
- `correctness:` the generated catalogue still cited `activationCommit`, a
  function this unit renamed — **fixed**, with the two enforcing strings whose
  signatures had drifted.

Second read, a fresh context given only the diff of those fixes and the same
two criteria, as ADR-017 decision 3 bounds it. Thirteen findings:

- `correctness:` the shared reader took the record's id and dropped its file,
  so a record whose filename does not match the id it declares had no history
  at all — no arrival, no merge, and both records bucketed together as *not yet
  committed* — **fixed**, the file the record sits at is one of the names
  walked. The repository that shape needs is already refused by `schema`, which
  requires a record's name to match its id, so the evasion needed an
  already-red repository; a reader that is sound only because another rule
  fires is the substitution this note's own soundness page is about.
- `correctness:` `readyBehind` false on both merge shapes made `transition`
  print *declare `ready` on the branch first* at a branch that had — **fixed in
  the message**, which now names both halves of the remedy: the branch declares
  `ready` in the administrative commit, and the trunk records `done` in a
  commit of its own after the merge. Both are true whichever half is missing,
  and the refusal itself stays: the trunk's own line did go `running` → `done`.
- `correctness:` the two `condition` columns still described the behaviour
  before this unit — one *change* taking two paths to done, and a `ready` read
  *from the history* — while the new tests assert the opposite — **fixed**, and
  the catalogue regenerated.
- `correctness:` the unit test for the per-commit grouping passed no
  integration state, so both arrivals bucketed under the same *not committed
  yet* key and the test read the same before and after the change — **fixed**,
  it now names one commit for both and, in a second case, one each.
- `shrink:` the two-shape list was still built by hand in two places with the
  same reason in prose twice — **fixed**, `recordShapes(id, file)`.
- `shrink:` an options bag for one boolean and a one-element array spread —
  **fixed**, `recordHistory(range, shapes, firstParent)`.
- `shrink:` the arrival bucket did the Map's job and the message's at once —
  **fixed**, the key is the commit or nothing and the prose is written where
  the message is.
- `shrink:` a rebuilt array per arrival where a push would do — **fixed**.
- `shrink:` the two integration fixtures shared twenty-two lines and differed
  in one `if` — **fixed**, one `twoIntegrations(dir, { inOneCommit })`.
- `shrink:` the record path reached the template through two channels —
  **fixed**, it is one field of the record's own fields.
- `shrink:` a call-site comment that restated the helper's docstring —
  **fixed**, only the sentence the call site needs is left.
- `correctness:` a comparison ref that is non-null but unresolvable reads as
  *no history*, which passes rather than reporting inconclusive — **refused**:
  `previousRef` is `comparisonRef`'s output, which is a `merge-base` or a
  `rev-parse HEAD` and so is always a resolved object id; a branch for a state
  the caller cannot produce is a branch nothing can test.
- `correctness:` a root-commit arrival makes `${commit}^` unresolvable and
  `readyBehind` quietly false — **refused**: a root commit has no trunk behind
  it to have declared `ready`, so false is the answer, and the refusal it
  produces is correct.

The fixes above are not read a third time.
