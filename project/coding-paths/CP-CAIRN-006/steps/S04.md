# CP-CAIRN-006 S04

### S04 — which commit, which branch, which checkpoint — **COMPLETE**

#### Plan

Three corrections of ADR-004, each about an identity the checker
resolves wrongly or not at all.

**Decision 1, the registration commit is the activation.**
`registration-base` finds it with `--diff-filter=A`, the first trunk
commit that added the record's file. A record landed as `draft` and
activated later is then judged against the draft's parent, which is not
the base the work forked from — on the adopter that produced a rewritten
`base_commit`, false by the specification's own definition. It becomes
the trunk commit in which the record's status became `running`, and the
refusal names the remedy.

**Decision 2, a running path names its remote checkpoint.** Fifteen
adopter units left it `unpinned`, so neither path could be resumed cold
from its record. A record declaring `running` that carries at least one
completed unit must name an object id in its checkpoint; `unpinned`,
empty or anything that is not an object id is refused under `work-unit`,
where the unit's other claims are judged, and the refusal says which
commit to write.

**Decision 5, and repair 007 of decision 6, the branch is resolved from
where the checker stands.** Every pull-request run of the installed
workflow is a detached checkout of the request head, on purpose. A rule
that reads the branch's history through `@{upstream}` finds nothing
there: the adopter's first supersession proof failed in the request's run
and nowhere else, while the push run on the same commit passed. The
branch's history is resolved in one order — the local ref, else `HEAD`
when the checkout is the request head, else the remote-tracking ref —
and the finding says which was used.

Definition-of-done item advanced: the sixth.

**This unit is the first half of the planned S04.** The plan carried
ADR-004's six corrections as one unit; they are two subjects, and
[`plan.md`](../plan.md) is amended to say so. What this unit resolves is
identity: which commit registered the path, which branch the checker
stands on, which commit the checkpoint names. S05 takes what a range may
be read as evidence of — decision 3 and repairs 005 and 006 — and the
later steps shift by one. The definition of done is untouched; item 6 is
advanced by both units.

Type `implementation`: behaviour changes, so the failing tests come
first.

Deliberately not in this unit: decision 3's path-scoped range rules and
repairs 005 and 006 (S05); decision 4's fixture sweep (S07). The concept
`trunk-registration`, which decision 1 says *may* gain a sentence, is
outside this path's `writes:` and is named in *Tried and rejected*.

- **`registration-base` reads the activation.** `activationCommit(commits,
  statusAt)` walks the record's history reachable from the trunk, oldest
  first, and stops at the first commit declaring `running`. Both record shapes
  are read: a record whose draft and activation sit under different names has
  no activation under either one alone. Not along first parents — an
  activation that arrives through a request is a merge, and that merge's first
  parent is the trunk at the merge, which the registrant could not have
  pinned.
- **`work-unit` judges the checkpoint.** `checkpointCommit(text)` reads the
  resume section through `resolveScopeSection`, the reader the file already
  has, and returns an object id or nothing. A record declaring `running` with
  a completed unit and no checkpoint is refused, and the refusal says which
  commit to write.
- **`resolveBranchRef` gives the branch's tip**, in ADR-004's order: the local
  ref, else `HEAD` when the checkout is detached — the request head — else the
  remote-tracking ref. `pathRemoteCheckpoint` uses it for the tip and reads
  `<branch>@{upstream}`, the branch's own, falling back to the remote-tracking
  ref when none is configured — so a detached request head is judged instead
  of reported as having no upstream, and a branch is never compared with the
  checkout's upstream. Both `remote-checkpoint` findings name the ref they
  read.
- **Six fixtures**: a branch forked from the draft rather than the
  activation; an activation that reached the trunk through a merge after the
  trunk moved; a record whose draft and activation sit under different names;
  a running path with a completed unit and an `unpinned` checkpoint; a
  detached request head with no local ref; and a rewritten published commit
  judged on that detached head.
- **The catalogue, the matrix and the module note** say what the three rules
  read now.

#### Review

First read, a fresh context given this unit's diff and the two criteria, and
nothing else. Nine findings; each with its disposition:

- `correctness:` the branch ref was resolved local → remote-tracking → HEAD,
  where ADR-004 decision 5 says local → `HEAD` on the request head →
  remote-tracking. The reader showed what that cost: on a detached request
  head the tip and the upstream were both `origin/<branch>`, so the comparison
  was tautological and **a rewritten published commit passed the merge gate**
  — `path-history` blocked on the branch and reported nothing on the one run
  that gates the merge — **fixed**, the record's order, with a fixture that
  amends a pushed commit and checks it both ways.
- `correctness:` the `missing` message claimed the remote did not hold the
  branch without ever asking — **fixed**; the claim is gone from the message
  and from the conformance row.
- `correctness:` `path-history` still said *is not an ancestor of HEAD* when
  HEAD was no longer what it compared — **fixed**, in the message and the row.
- `correctness:` a record landed flat as a draft and sliced into its folder at
  activation had its two states under two names; following one, the reader
  found no activation and emitted *fetch the complete trunk history*, a remedy
  that can never work — **fixed**, both shapes are read.
- `correctness:` the log reported a side-branch commit for a registration that
  arrived through a merge — **fixed with `--first-parent`**, and the second
  read showed that fix was itself wrong; see below.
- `shrink:` `checkpointCommit` hand-rolled a Markdown section reader the file
  already has, and was wrong about heading levels and case where
  `resolveScopeSection` is right — **fixed**.
- `shrink:` a second `rev-parse` in the catch block asking what
  `resolveBranchRef` had already answered — **fixed**.
- `delete:` the ref-provenance suffix and the two `remote-checkpoint` branches
  had no case that separated them — **fixed for the branches**, by the
  `path-history` fixture on a detached head; the suffix is output the DoD asks
  for and is read by the owner, not by a test.
- `yagni:` `activationCommit` was an exported one-liner whose test exercised
  `Array.find` rather than the change — **fixed**, the history walk moved into
  it, so what the suite tests is what differs.

Second read, a fresh context given only the diff of those fixes and the same
two criteria, as ADR-017 decision 3 bounds it. Seven findings:

- `correctness:` `--first-parent` turned a legitimate registration into a
  block. A record authored on a request pins the trunk tip its registrant
  saw; if the trunk moves before the merge, the merge's first parent is the
  trunk *at the merge*, which nobody could have pinned. My own fixture hid it
  by computing that value after the fact — **fixed**, the flag is gone, and
  the fixture now pins what a registrant can pin and moves the trunk before
  the merge.
- `correctness:` the comment justifying the flag said the opposite of what the
  flag does, and the fixture's assert message repeated the inversion three
  lines after asserting the contrary — **fixed** with the flag.
- `correctness:` `@{upstream}` is HEAD's, not the branch's, so standing on the
  trunk while naming a path branch compared that branch's tip with
  `origin/main` and **blocked a repository where nothing had been rewritten**
  — **fixed**, the upstream is now `<branch>@{upstream}`, which also closes
  the remaining tautological arm.
- `correctness:` the conformance row claimed a property — *never compared with
  itself* — the code did not yet have — **fixed** with the above, and the row
  now says what it does.
- `delete:` `declarationOnTrunk` was left dead when its only caller was
  inlined — **fixed**, deleted; the one sentence worth keeping moved to the
  reader that now states the rule.
- `native:` the explicit loop in `activationCommit` bought nothing over
  `Array.find`, which already short-circuits — **fixed**, and the test that
  asserts it stops at the activation still holds.
- `delete:` the flat record shape had no adversarial case — **fixed**, not
  deleted: a record born in its folder, migrated to the flat shape and
  activated there, is the case, and dropping the shape turns it red.

The fixes above are not read a third time.
