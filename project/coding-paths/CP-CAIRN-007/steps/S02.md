# CP-CAIRN-007 S02

### S02 — one run per commit that can land — **COMPLETE**

#### Plan

Make this repository's CI adapter judge each commit that can land exactly
once and write a red run's reading while it happens: the `push` trigger's
branch list becomes the trunk alone, the request's run keeps judging the
request head
([ADR-005](../../../../docs/adr/ADR-005-one-run-per-commit-that-can-land.md));
the checker's step carries `GITHUB_TOKEN`, the fifth debt of path 2, so
the profile line reads the trunk's rules instead of *forge not read* on
the one run that is the merge gate; a step that runs only on the
checker's failure prints the post-mortem into the log under its own name
and, on a request, posts it once as a comment, committing nothing
([ADR-014](../../../../docs/adr/ADR-014-two-tools-of-1-1.md) decision 1);
the suite runs before the checker as `cairn-test`, with `npm test` kept
as its alias so the bootloader's command list stays true (ADR-014
decision 2).

Definition-of-done item advanced: the second.

Type `implementation`: the adapter, its test, the package scripts, the
affected module note, this step. Failing test first — the four facts
above are behaviour, and the incident each of them exists for is one a
predicate can hold even though the workflow is YAML.

`writes:` widened by one file, `tools/cairn-workflow.test.mjs`: the
adapter had no test, and the two records it implements were both written
after a wrong answer here cost something — a green push run beside the
red request run that was the gate, and five post-mortems read by hand
after the fact. Putting those assertions in the post-mortem tool's own
test file would have made that file about two things.

Deliberately not in this unit: `workflow()` in `tools/cairn.mjs`, the
KIT's copy of this adapter, which item 7 of the definition of done holds
unchanged — see the debt below; the audit and live-view tools (S03); the
owed sentences of the skills and the template (S04), including the unit
skill's *then read the request's run, if a request is open*, which
ADR-005 also names; the module note's prose, which S05 rewrites against
the whole candidate.

**The debt this unit found.** ADR-005 and ADR-014 decision 1 change *the
kit's CI adapter*, and the kit generates it from `workflow()` in
`tools/cairn.mjs`. Row 3 of the register writes
`.github/workflows/cairn.yml` — this repository's installed copy, which
is what this unit changed — and row 4 writes `tools/cairn.mjs` but names
neither record. So no row of the register owns the generator for these
two, and an adopter installing 1.1 would receive a workflow that still
runs on `path/**`, still reports the forge unread, and has no red-run
step. Named here, carried to this path's journal entry, and for the owner
to place on row 4 or on a row of its own; it does not block this path.

**Observed and left true.** `AGENTS.md`'s command list still reads
`npm test`, which the alias keeps true. ADR-014 decision 2 also asks the
bootloader to *say so there* — that it is an alias; `AGENTS.md` is row
4's write surface and the sentence is named there, not owed by a document
this unit made false.

#### Review

First read, a fresh context given this unit's diff — the adapter, its
test, the package scripts and the module note — and the two criteria, the
ladder and correctness, and nothing else. Sixteen findings; each with its
disposition:

- `correctness:` the job's `permissions:` block omitted `actions: read`,
  and an explicit block sets every scope it does not name to `none`. The
  red-run reading calls the forge's `actions/runs` endpoint, so the step
  would have printed *the forge answered HTTP 403* for the one fact
  ADR-014 decision 1 was written to capture — **fixed**, the scope is
  declared with that reason beside it, and the test now pins the whole
  granted list rather than three memberships.
- `correctness:` mapping `GITHUB_TOKEN` into the checker's step may still
  leave the profile line unread: `readForge` fails the WHOLE read when a
  ruleset cannot be fetched, and the ruleset endpoint wants an
  administration scope that a workflow `permissions:` block cannot grant
  at all. The module note asserted the outcome — **fixed**: the note now
  says the read is attempted with the forge's own token and that what the
  token may read is what the line reports. The outcome itself is a fact
  this unit can only learn from a real run, and it is read below under
  *Verification*.
- `correctness:` the step's shell is `bash -e`, so a non-zero exit from
  the tool would abort before `cat` and before `gh pr comment` — losing
  the reading on exactly the run it exists for — **fixed**: the
  redirection falls back to a line saying the tool stopped, and the log
  and the comment both still happen.
- `correctness:` on a request from a fork the token is read-only whatever
  the block says, so the comment cannot be posted, and the request
  reading's `head=owner:branch` never matches a fork branch —
  **accepted**, and said in the comment: this is a sole owner's
  repository and a fork request is not a shape it has. Naming it is the
  whole of the fix; making the workflow handle a fork would be building
  for a case that does not exist.
- `correctness:` ADR-005 and ADR-014 decision 1 name *the kit's CI
  adapter*, and the kit generates it from `workflow()` in

  in the plan above, carried to this path's journal entry, and is the
  owner's to place. The reader's suggestion to pin the kit's current
