# CP-CAIRN-007 S08

### S08 — the record says which step it is on — **COMPLETE**

#### Plan

Move `current_step` from `S01`, which it has declared since
registration, to this step.

The violation: `current_step` is how the `review` rule chooses which
step record to read for the `#### Review` section — `workUnits.find(unit
=> unit.step === front.current_step)`. Declaring `S01` for seven units
meant the rule read `S01.md` every time, and passed every time, because
that record does carry a review. So the units of this path were gated on
one step's review section, read seven times, while six others were never
read by the gate at all. Nothing is missing — all seven records carry the
section — but the gate was not doing what it says it does, and a record
that declares `S01` after seven steps is false about itself.

It is caught now because the closure wanted to move the field and may
not: `closureMutableFields('ready')` is `status` and `subject_commit`,
and nothing else. That is the rule working — an administrative commit
must not quietly correct the record it is closing.

Definition-of-done item advanced: the ninth, which asks that every
completed step have its record and its review; this is the unit that
makes the gate read them.

Type `repair`: the corrective change and a step naming the violation. No
superseding record is owed — no step record was edited, and every one of
them still preserves the blob that added it. No test: nothing under
`tools/` changes, and the rule that reads the field is coding path 2's,
already written and already correct.

Deliberately not in this unit: anything else. A candidate is the last
unit's commit, so a repair that carried a second change would make the
closure judge two things at once.

- `delete:` **the sentence buys nothing, because the field can only ever
  weaken the rule.** `workUnits.find(u => u.step === current_step) ??
  workUnits.at(-1)` runs over a list `pathWorkUnits` sorts ASCENDING by
  ordinal, so `at(-1)` is the unit just written and the `find` can only
  ever select an OLDER one. The reader proved it against `evaluate()`: a
  record on `current_step: S01`, with S01 reviewed and S02 not, raises no
  finding at all — while the same repository with the field ABSENT blocks
  on `S02.md`. Pointing the field at this step gives exactly the verdict
  omitting it would. A sentence asking writers to maintain it therefore
  restores the default by hand, which is the symptom; and seven units of
  this path running green on a stale `S01` is the proof that prose is not
  what holds this. **Fixed by reverting my own fix**: the skill sentence
  and the template comment are gone, and the root cause is on row 5 of
  the register beside the other reading that lies — delete the
  `find(…) ??` so the rule judges the ledger's newest, which is the unit
  under review, and `current_step` becomes decoration that can go with
  it.
- `correctness:` both sentences stated the gate's behaviour as absolute
  when it is not — with no `current_step`, or one naming a step with no
  block, the rule reads `workUnits.at(-1)`, and the suite has a case for

  page. **Moot** with the revert; the accurate form is what row 5 carries.
- `correctness:` the imperative was unconditional and trapped the

  revert, and a good reason not to have added it.
- `shrink:` the template comment was the deletable half of a duplicate,

- `shrink:` the clause hung off the step-record half of the sentence
