# CP-CAIRN-009 S03

### S03 — the pointer page, `update` and `status` — **COMPLETE**

#### Plan

An installed repository gets one generated page that says which release
it carries and what the kit owns, and `update` stops protecting a file
that holds nothing of the adopter's while gaining the two things it
could not do — say what a release changes in a file it must not rewrite,
and hand over the release's version of one the owner names. It is the
least because the lock already tells pristine from edited for every file
it names, and every reading here is that one fact spent better. It does
not touch the manifest, the chapters or the generated adapter.

Definition-of-done items advanced: the fifth (the pointer page) and the
sixth (`update` and `status`).

Type `implementation`: the installer, its tests, the `tools/` module
note and this step move together. Every behaviour change is written as a
failing assertion first, on an installation the test builds and edits.

**The read S02 owed, first.** S02's review fixes never reached a second
context — four of seven agents hung. That read is made before this
unit's own work and its findings are dispositioned in the section below,
against S02's saved fix diff.

**The defect S01's review left here.** `applyAdopt` writes the migrated
configuration to disk but `writeLock` digests the generated one from the
plan, so `status` reports an untouched `cairn.config.json` as *edited*
straight after `adopt`. Verified at `base_commit`, so it predates this
path. `main()`'s update branch already carries the one-line guard —
`plan.files.set('cairn.config.json', …)` — and this unit moves it where
both commands read it, which is also what the pointer page needs, since
a page generated at plan time and rewritten at update time would
otherwise be locked at the wrong digest.

Deliberately not in this unit: `REFERENCE_TOOLS`, `cairn-learn`'s
manifest entry, Ponytail, the generated workflow and request template and
the conformance page's kit line (S04); chapters 3 and 6, the concepts and
the layout (S05); this repository's architecture index and the register
(S06). The release's one-line note per changed template, which ADR-015
d2 says `update` prints beside the diff, is row 6's: nothing produces
such a line yet, and the decision already says the diff alone is printed
where it is missing.

- **`pointerPage`** and `POINTER_PAGE = 'cairn/README.md'`, generated at
  `init` and at every `update` and written by no hand: what Cairn is in
  the manifesto's own sentence, the release and the full commit it was
  cut from, the six chapters and the six skills each linked at that
  commit with a line on what it is for, every file the kit owns —
  itself and the lock included, because `status` reads both — with the
  sentence that `update` rewrites what still holds exactly what the kit
  wrote and never rewrites what you edited, and a *To reconcile by hand*
  section that is empty until an update leaves something in it (ADR-013,
  ADR-015 d2). The bootloader's *start here* list gains it as item 6.
- **`installationStatus`**: a pristine file whose template changed is
  written, whoever owns it (ADR-015 d1). The `review` action and its
  line in `describeStatus` are deleted; ownership now decides only what
  happens to a file that **left** the kit. Two existing tests asserted
  the rule this supersedes — *a host file is the adopter's even when
  pristine: reviewed, never rewritten* — and were rewritten to the new
  rule, named here because a test changed to match the code is worth
  seeing.
- **`applyUpdate`** reads the installation twice on purpose: once to find
  the edited files whose template the release changed, then — with the
  pointer page rebuilt to name them — again, so the page the lock digests
  is the page that lands. For each such file it prints what the release
  changed, and its report ends with the list to settle by hand, which the
  page carries to disk so the work outlives the terminal (ADR-015 d2).
- **`templateDiff`** is Git's own `diff --no-index` against the template
  in a temporary file, not a diff written here: the kit already requires
  Git, and a diff implemented in this file would be more code than the
  thing it compares. `--no-index` exits 1 when files differ, which is the
  answer and not a failure; an empty stdout is the failure, and is
  reported as a diff that could not be produced, never as no difference.
  The headers name a temporary path and an absolute target, so only the
  hunks are returned and the caller captions the two sides.
- **`takeRelease`** and `update --take <path>` (ADR-015 d3): one named
  file becomes the release's version, the command prints the lines it is
  about to discard rather than describing them, says what the file was,
  and touches nothing else. A path the release does not carry is refused
  by name.
- **`applyAdopt`** sets the migrated configuration into the plan instead
  of writing it past the plan, so `writeLock` digests what actually
  landed. This is S01's review finding, verified there at `base_commit`;
  the same one-line idiom `main()`'s update branch already used, moved to
  where both commands read it — which is also what the pointer page
  needed.
- **`docs/modules/application.md`** and **`spec/reference/conformance.md`**:
  what `update` does and refuses, the pointer page, and the measurement —
  32 files and the lock on `ci`, 31 on `local`. The conformance row's
  closing clause stated the rule ADR-015 d1 replaces and was corrected.
- **Tests, each written first and seen red**: the page's contents and the
  bootloader's link to it; a pristine host file rewritten and an edited
  one explained, with the lock agreeing with what was written; `--take`
  on one file leaving its neighbour alone; and `adopt` no longer calling
  an untouched configuration edited.

#### Self-review

- `shrink:` `applyUpdate` first wrote the pointer page outside the plan
  and then carried a second block to write it again when the first loop
  had not — a condition whose truth depended on a status computed before
  the page was set, which is the kind of line nobody can read twice the
  same way. Replaced by reading the installation twice, which is pure and
  cheap, so the ordinary write loop handles the page like any other file.
- `correctness:` `--take` said *discarding what was edited here*, which
  describes the discard rather than showing it. ADR-015 d3 asks the
  command to say what it is about to discard, and the reason to run it is
  a claim about lines; it now prints them, reusing `templateDiff`.
- `shrink:` `templateDiff` returned Git's whole output, whose headers name
  a temporary file and an absolute path — noise a reader has to skip past
  every time. Only the hunks are returned; the caller says which side is
  which.
- `delete:` `mkdirSync(dirname(scratch))` before writing into the system
  temporary directory, which exists by definition.
- `delete:` the `review` action and the `describeStatus` line that printed
  it — nothing produces it once ADR-015 d1 lands, and a branch nothing
  reaches is a branch that will be wrong when someone reaches it.
- `stdlib:` the diff is Git's, not one written here; `tmpdir()` is
  `node:os`. Nothing was hand-rolled that the ecosystem already ships.
- `native:` `applyAdopt`'s fix is the idiom `main()` already used one
  branch away, moved rather than reinvented.
- Two tests changed to match the code, not the reverse: both asserted the
  pre-ADR-015 rule that a pristine host file is reviewed and never
  rewritten. Named in the Work section above so the change is visible
  rather than buried in a diff.
- No widening of `writes:`; every file here was already declared.
- Net across the six files, before this step record: 345 added, 30
  removed — of which the installer is +196/−12.

#### Review

**How this read was made, and what is weaker about it.** Three fresh
contexts were given this unit's diff and the two criteria. All three
hung: two stopped at eleven minutes having emitted one line — *"I'll
start by reading the diff"* — and the third, given the whole diff inline
so that it needed no tool call at all to begin, was stopped at eleven
minutes having emitted **nothing**. That last one matters as evidence:
the stall is in the request, not in a first tool call, so there is no
prompt shape that works around it. Across S01 to S03, seven of eleven
review contexts hung; the four that returned took between 140 and 495
seconds, so a stalled one and a working one are indistinguishable for
the first minute.

The read below was therefore made **by this same context**, cold against
the two criteria and the diff as written, which is weaker than what
`cairn-unit` movement 4 asks for and is recorded as such rather than
dressed up. It is not nothing — it found three defects, two of them
behavioural — but a second pair of eyes would have been better, and the
debt S02 raised is now a pattern rather than an incident. What it means
for the path is in the resume section.

Findings, each with its disposition:

- `correctness:` `pointerPage(options, commit, …)` never read `options`
  in its body — a parameter three call sites passed and nothing used —
  **fixed** before the diff was sent out, by deleting it.
- `correctness:` `update --take <path>` wrote the file and left the lock
  alone, so the file it had just replaced with the release's version
  still read as *edited* on the next `status` whenever the template had
  actually moved — which is the only case anyone runs the command in.
  ADR-015 d3 says the file becomes pristine **at the new release**, and
  pristine is a statement about the lock, not about the bytes. **Fixed**:
  that one manifest entry is updated, and only that one, because the
  installation is still at the release the rest of it carries. The test
  that passed before did so because it moved no template; a case that
  moves one was written, and it failed first.
- `correctness:` `update --take <path> --dry-run` wrote the file. The
  take branch returns before `applyUpdate` and never saw the flag —
  the one place in the command where `--dry-run` silently did the thing
  it promises not to. **Fixed**, with a test.
- `shrink:` `templateDiff`'s scratch file can collide between two
  concurrent runs — **refused**. The name is the digest of the template,
  so a collision means identical content; there is nothing to race over.
- `correctness:` `applyUpdate` mutates `plan.files` under `--dry-run` —
  **refused**. Nothing reaches disk, and the status it returns is the
  status of the update it is describing, which is what a dry run is for.
