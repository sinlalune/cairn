# CP-CAIRN-001 S06

### S06 — one command installs, inspects, updates and adopts, and the kit is 26 files that link the specification — **COMPLETE**

#### Plan

Turn the 0.2 installer into the `cairn` command: `init` from a thin kit that
links the specification at the pinned commit instead of copying it, `status`
against the lock, `update` by lock digest, and `adopt` for a repository that
carries the protocol without a lock. Make the package publishable. Rewrite
this repository's own lock with the command. Move the path convention beside
the execution protocol, as the owner ruled. Run `adopt` on Atomik at
`46bdd11` as the acceptance test and record what it found.

Deliberately not in this unit: publishing to npm and tagging (S08); the
README and the site (S07); migrating an adopter's records into the 1.0
shapes, which is judgement — `adopt` reports them and touches none.

- **The npm name is taken.** `cairn` is another package at 0.8.0, so the
  package is `cairn-protocol` and its binary is `cairn`: `npx cairn-protocol
  init`, and `cairn init` once installed. The owner asked for `npx cairn`;
  this is the nearest honest thing, and it is stated wherever the command is
  named.
- **The kit is thin.** `init` writes 25 files on the `local` profile and 26
  on `ci` — the five reference tools, the eight skill files, the
  configuration, the bootloader, the binding, the workflow and the request
  template, the roadmap register, the two plane indexes, the module-notes
  index with the area note, and the adopter's own concept index — plus the
  lock. Under thirty, from 101. It copies no specification and no path
  convention: the bootloader, the binding and the skills link them at the
  commit the kit was cut from, so a repository installed today resolves to
  the text it was installed from, and `roots.concepts` points at the
  adopter's own wiki, never the protocol's. No folder logs, no journal
  folder until the first integration, no architecture or decision folder
  until the first page: a folder appears with its first file.
- **The lock records the kit's bytes.** One digest per kit file as the kit
  wrote it — not as the tree holds it — so `status` tells pristine from
  edited from missing, and says whether a newer release exists.
- **`update`** rewrites pristine kit files, restores missing ones, keeps
  edited ones and says so, deletes pristine files that left the kit, reports
  edited ones that did, migrates the configuration from schema 1 field by
  field, regenerates the view and writes the new lock. The decision is a pure
  function over the lock, the plan and a reader of the tree, tested on a
  synthetic tree.
- **`adopt`** turns a repository carrying the protocol without a lock into an
  installation: the configuration migrated with the host's answers kept and
  an adapter name outside the vocabulary read as `manual-git`; the tools and
  the skills written; every host file kept where it exists and written
  where it is absent; the view regenerated; the lock written; and every 0.2
  shape reported — the copied specification, the sessions, audits and briefs
  folders, the 0.2 tools and their tests, the flat records — with none of it
  deleted. A repository with a lock is refused and sent to `update`.
- **Atomik at `46bdd11`, adopted.** The command migrated its schema-1
  configuration (`master`, `atomik`, its six areas and three migration lists
  kept; `sharedFiles` and `staleAfterDays` dropped; `manual-git` kept as
  declared), wrote 16 files, kept 9 host files, and reported 44 stale
  shapes. Its gate then failed on five broken links — three in
  `docs/fixtures/`, which portray another vault, one in a fixture into a
  sources folder, one in the flat journal — that the 0.2 checker had exempted
  by name. Those exemptions were Atomik's, and they left in S02; the links
  are Atomik's adoption work, and `adopt` said so rather than passing over
  them. The lightweight opening on its running records, its copied
  specification and its 0.2 tests are the rest of that work.
- **This repository's own lock, rewritten.** `update` wrote the roadmap
  register and the documentation index, kept twelve host files that this
  repository edits — it is the source — and deleted eleven 0.2 folder logs
  and empty-plane indexes the kit no longer defines; the last folder log went
  with this unit. The lock now names release `1.0.0-rc.1` at the S05 commit
  and 26 kit files.
- **The path convention lives beside the execution protocol**, at
  `spec/reference/paths.md`, as the owner ruled: one portable root. Its links
  are relative to the specification now; the bootloader here points at it,
  and an installed bootloader links it at the pinned commit.
- Rejected: installing `cairn.mjs` into the adopter's tools. The command runs
  from the package against the lock; a local copy would copy from itself.
- Rejected: `adopt` deleting the 0.2 shapes it recognises. They are the
  adopter's, some of them are its history, and a migration that deletes what
  it does not understand is the overwrite the 0.2 installer refused.
- Rejected: pinning the specification links at a release tag. The tag does
  not exist until S08 and a link to it is dead until then; the source commit
  is exact, is already on the forge, and is what the lock records anyway.
- Found and fixed: `status` listed the generated view as a file `update`
  would rewrite, because the plan carries a placeholder and the lock the
  generated bytes; the view is regenerated, never compared.
