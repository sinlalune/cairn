# CP-CAIRN-001 S04

### S04 — the pull request is the closing record, and the checker proves only what Git holds — **COMPLETE**

#### Plan

Make `pull-request` the default integration transport with `manual-git` as
the fallback, both named in the configuration. On `pull-request` the request's
description is the coherence review and its approval the closing acceptance;
the checker reads none of that and proves what Git holds. On `manual-git` the
same review and acceptance are one closing record in the path folder, which
the checker reads. Derive the base `T` of the acceptance-drift predicate from
Git rather than from a record, so the drift check is the request's own check.
Drop the session and audit folders from the Cairn-defined tree.

Deliberately not in this unit: `npx cairn` and the lock (S06); the skills
(S05). This repository's own ruleset already requires the request, so nothing
on the forge changes.

#### Work

- **Two transports, named.** `transport.registration` and
  `transport.integration` are `pull-request | manual-git` in schema 2, and
  `cairn-init` writes `pull-request` unless told `--transport manual-git`. This
  repository's configuration says `pull-request`; it always was one.
- **`acceptance` reads the transport.** On both: a ready candidate is an
  ancestor followed by exactly one administrative commit that changes nothing
  outside the closure surface and moves no field but status and subject; a
  done candidate is reachable. On `manual-git` additionally: the closing
  record `closing-<C>.md` in the path folder names exactly `C` with its
  fields, is a completed review — a verdict from the vocabulary, at least one
  answered question, no scaffold placeholder — and its dispositions cover
  exactly the advisories attested at `C`; a self-issued acceptance is
  reported. On `pull-request` those four readings are the forge's, and the
  conformance page says so in the row's third column.
- **`T` is derived.** The branch merged the trunk in before the candidate, so
  the base the acceptance was read against is the merge-base of the branch and
  the trunk. `acceptance-drift` computes it and diffs the trunk from there; no
  record names it, the closing record on `manual-git` states it for the
  reader, and the request's own check is the drift check the plan asked for.
- **`scope-digest` reads the opening.** The acceptance in force is the opening
  block, and the definition of done must digest to what it accepted; on
  `manual-git` the closing record's re-computed digest must agree.
- **At `done` the checker proves reachability.** The 0.2 count of "exactly two
  commits after the candidate" was a proxy that a merge landing beside other
  paths breaks; the closure surface is proved at `ready`, on the exact commit
  that lands, and `journal-entry` and `transition` prove the rest.
- **`cairn-audit` is the closing scaffolder for both.** It prints the
  request's description for the current candidate — candidate, derived base,
  the digest line, the four questions, the advisories to disposition, the
  roles — or, on `manual-git`, scaffolds `closing-<C>.md`. Its `--check` mode
  is gone: the checker reads the record itself. The kit installs
  `.github/pull_request_template.md` so every request starts in the review's
  shape; this repository has it too. The fill predicate — verdict stems, an
  answered question, no placeholder — moved into the checker as pure code.
- **The session and audit folders left the tree.** The initializer creates
  neither; `project/audits/` is deleted here and `project/sessions/` stays as
  the history of one opening record; immutable records are the closing record,
  the journal and the steps. The redaction index walks the project plane.
- **The fixture harness closes on both transports**, installing the repository
  with the transport under test: the green committed closure runs twice; the
  four `manual-git` fixtures cover a missing closing record, a scaffold, an
  undisposed advisory and a closing digest the opening did not accept, with
  the record scaffolded by the real command; the `pull-request` fixtures cover
  a moved closure surface, implementation after the candidate, an edited
  definition of done, a rewritten step, drift on the remote trunk and a
  provisional candidate. The suite is 221 subtests.
- **The pages say the two transports**: the specification's integrating unit
  is the commit after the forge's merge or the merge itself; the closing
  acceptance, coherence audit, integration transport, administrative closure,
  implementation candidate, acceptance drift and lightweight-path concepts
  describe the request and the closing record; the human-records page carries
  the request's description and the closing record's template; operations has
  the two closing and two integration sequences; the layout and the
  configuration name the template and the vocabulary.
- **Landed in two commits, stated.** A staging command named the already
  removed `project/audits/` and failed, and the commit that followed carried
  only that deletion; it was pushed before the error was read, and a published
  commit is never rewritten here. The completing commit carries everything
  else, and the two together are this unit. The lesson is the step's own: read
  the exit code of every command in a chain, not only the gate's.
- Rejected: reading the request's approval from the forge in the checker. It
  needs a network and a token in the one tool that must run dependency-free
  and offline, and the forge already refuses to merge without it: re-checking
  a native guarantee is the invented solution beside the native one.
- Rejected: keeping a closing record on `pull-request` "for the archive". The
  request is durable on the forge and the journal entry names the candidate;
  a second copy of the review is where the two disagree.
- Rejected: `done` recorded inside the merge on `pull-request`. A forge merge
  carries no edits of its own, and a path branch cannot claim `done`, so the
  integrating unit is the trunk commit that follows.
