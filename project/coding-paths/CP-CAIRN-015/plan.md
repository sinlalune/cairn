# CP-CAIRN-015 — forward plan

Read when planning, never before every step. Each item is one work unit.
A unit that changes what the kit writes changes the lock, its test and
the layout reference's lock row in the same commit; a unit that changes a
report changes `status` and the pointer page together, since they read
one predicate.

1. **S01 — the installer reads what the repository declared.** Every
   declared root, none derived where one is named, the plan's assertion
   (ADR-033 decision 1); `update` declining a host file, the lock's field,
   `status` reading *declined*, the pointer page (ADR-033 decision 2); the
   documentation index's two sentences (ADR-033 decision 3); the backlog
   item for the empty `steps/` folder.
2. **S02 — what `update` and `status` report.** One function building the
   plan (ADR-034 decision 4); one predicate for the reconcile list, the
   view on neither side (ADR-034 decision 1, Atomik's third observation);
   the files an update starts managing (ADR-034 decision 3); the release's
   stamp on every generated page and the byte-equal assertion (ADR-034
   decision 2, Atomik's first); the host-baseline mark in the lock
   (Atomik's second).
3. **S03 — what `adopt` and `init` say and refuse.** The red-gate line
   under the stale list (ADR-033 decision 4); the shape that wants a link
   exemption (ADR-037 decision 2); the two refused pairings with the
   installer's one GitHub reading and its one line when it did not read,
   the configuration and conformance rows (ADR-032 decision 4); the pilot
   registering through a request on `pull-request` (ADR-032 decision 2).
4. **S04 — what the kit installs.** `cairn-update` in the manifest, the
   pointer page and the generated bootloader (ADR-035); `feedbacks/` and
   its index naming the type (ADR-038 decisions 2 and 5);
   `project/backlog/` and its index (ADR-041); the changelog shipped,
   linked by `status` and the pointer page (ADR-039).
5. **S05 — Ponytail and the harness.** The two skills fetched from the
   latest release, the pin gone, the version in the lock and in `status`,
   the offline line (ADR-036 decision 1); every skill written where the
   harness loads it, owned by the lock, the unit stating link or copy and
   which harnesses (ADR-036 decision 2).
6. **S06 — the two templates and the module note.** The pilot's record as
   a plain list (ADR-042); the generated request template's *Coherence*
   section, every blank backticked, the no-bare-blank test (ADR-043,
   Atomik's fourth); `docs/modules/application.md` current; the layout
   reference's lock row final.
7. **S07 — the candidate.** Trunk merged in, gates bare, the register's
   row 3 of 1.2 naming this path; then the close skill's order: the
   administrative commit, the fresh-context coherence read in the
   request's description, the owner's try of `init`, `update` and `adopt`
   on a scratch repository, the merge.

## What the units must not do

Change the checker, the audit or post-mortem tools, the workflow, the
skills or the README. Write a figure of the kit anywhere but as a
measurement the step reports — row 5 writes it once. Let the installer's
GitHub reading reach the checker.
