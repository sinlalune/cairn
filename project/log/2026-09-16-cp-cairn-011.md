## What the closing found, and what that says

The kit's first run against the repository that ships it read that
repository as an adopter: it planned three concept folders under
`spec/concepts/`, the protocol's own wiki, because the binding names that
root, and `update` has no way to decline a host file. The three were
deleted after each run and every `status` here reports them missing.
That is the reading a repository gets when it binds its wiki where the
protocol keeps its own, and it is on the 1.2 row rather than fixed in a
release.

The owner's try found a defect the quick start had hidden. Quick start 1
commits the installation before the first check, and the step's proof
did too; the owner ran the check first, and `cairn-check` on a repository
with no commit died with Git's own stack trace — `fatal: ambiguous
argument 'HEAD'` — instead of a message naming the remedy, as ADR-008
decision 6 asks of every refusal. Reproduced on a fresh `init`. The
checker is outside a release path's writes, so it is left as it was and
named below.

An automated reviewer on the request built its own squash of the branch
onto the trunk to read the tree and warned against landing that squash.
Nothing had been squashed; the warning was the protocol's own rule, and
the disposition was written on the request. The repository allows squash
and rebase merges beside the merge commit, so the rule holds by the
owner's choice at each click; whether to close the two other methods in
the settings is the owner's.

The fixture suite went red once, on S01's first run, on a fixture that
met `record-integrity` where it expected nothing, and green on every run
after — seven runs across the path. The test's name was lost to the tail
of its output. Not diagnosed.
