# A remedy that lives in a feedback file does not bind the next writer

**Movement:** cairn-close, steps 3 and 4, on `pull-request` transport with one
owner holding every role — the same movement as
[`2026-09-17-ecos-merge-before-administrative-commit.md`](./2026-09-17-ecos-merge-before-administrative-commit.md).

**Cost:** that file already named this failure and already named its remedy:
land `A` on the branch before asking for the reading. CP-R4-001 followed it
and said so in its journal. CP-R3-001 did not, and paid the same cost again —
the merge landed while the record said `running`, and `A` had to be repaired
onto the trunk afterwards with two commits and a paragraph explaining why.

The writer of this path read `AGENTS.md`, the path convention, the binding,
the live view, the path record and `cairn-close` in full, as movement 0 asks.
`feedbacks/` is in none of those. Nothing in the reading order reaches it, so
a remedy parked there is invisible to exactly the person it was written for,
and the only thing that carried it from R4 to here was that a reader happened
to open a neighbouring journal entry.

**Change to Cairn that would remove it:** a feedback file is a proposal, not a
rule, and the kit should say which it is. Either fold an accepted remedy into
the skill it corrects — `cairn-close` step 4 gaining one sentence for the
single-owner case would have ended this — or have `cairn-unit` movement 0
name `feedbacks/` in the reading order, so a proposal at least gets read
before the movement it corrects is performed. The first is better: a rule that
has to be rediscovered in a folder of essays is not a rule.
